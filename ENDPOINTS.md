# Healz Web — наблюдавшиеся маршруты и endpoints

Дата исследования: 29 июля 2026
Среда: публичный `https://app.healz.ai`, мобильный Chromium/Playwright.
Статус документа: описание фактически наблюдавшегося поведения, а не официальный API-контракт Healz.

## Принципы интеграции

- Мобильное приложение не вызывает закрытые endpoints Healz напрямую.
- Авторизация и загрузка остаются внутри публичного сайта в WebView.
- Нативная часть передает выбранные локальные файлы стандартному HTML file input; запрос формирует сам сайт.
- В коде не фиксируются email, одноразовые коды, cookie-значения, пользовательские данные или содержимое документов.
- Изменения серверного API не должны требовать обновления приложения, пока сохраняется стандартный web-flow.

## Маршруты страниц

### `GET /`

Публичная landing/auth-страница.

Наблюдавшееся поведение:

- при загрузке проверяет текущую сессию;
- кнопка прикрепления файла у неавторизованного пользователя сначала открывает auth-modal;
- после успешного входа пользователь может перейти в приложение.

### `GET /app/chat`

Основной интерфейс чата.

Наблюдавшееся поведение:

- без действующей сессии отвечает редиректом `307` на `/`;
- с действующей сессией открывает чат;
- содержит скрытый стандартный input примерно следующего назначения: `type="file"`, `accept="application/pdf,image/*"`, `multiple`;
- выбор файла запускает загрузку документа, после чего карточка файла появляется в composer;
- сама отправка сообщения остается отдельным действием пользователя.

## Авторизация

### `GET /api/auth/get-session`

Назначение: проверить текущую веб-сессию.

Наблюдался:

- при открытии публичной страницы;
- после успешного подтверждения одноразового кода;
- при восстановлении уже существующей сессии.

Приложение не парсит тело ответа и не хранит auth-token самостоятельно. Состоянием авторизации управляют WebView и сайт.

### `GET /api/signup-modal`

Назначение: получить данные/состояние модального окна авторизации.

Наблюдался при открытии auth-modal, в том числе после попытки прикрепить файл без авторизации.

### `POST /api/auth/email-otp/send-verification-otp`

Назначение: отправить одноразовый код на email.

Наблюдавшийся JSON-запрос:

```json
{
  "email": "<user email>",
  "type": "sign-in"
}
```

Тело ответа не является частью нативного контракта и приложением не обрабатывается.

### `POST /api/auth/sign-in/email-otp`

Назначение: подтвердить вход одноразовым кодом.

Наблюдавшийся JSON-запрос:

```json
{
  "email": "<user email>",
  "otp": "<one-time code>"
}
```

После успешного ответа сайт повторно запрашивает `/api/auth/get-session` и устанавливает persistent cookies.

### Cookies сессии

Наблюдались следующие имена cookies:

- `__Secure-better-auth.session_token` — `HttpOnly`, `Secure`, `SameSite=Lax`, долгоживущая сессия;
- `__Secure-better-auth.session_data` — `HttpOnly`, `Secure`, `SameSite=Lax`, более короткий кэш данных сессии;
- `hlz_signed_up` — признак завершенного signup-flow.

Значения cookies не читаются JavaScript-мостом и не копируются в нативное хранилище. WebView работает не в incognito-режиме и сохраняет их штатным Android CookieManager.

Проверенный результат: холодный перезапуск браузерного профиля с тем же хранилищем открыл `/app/chat` без повторного OTP.

## Загрузка документов

### `POST /api/documents`

Назначение: загрузить выбранный документ.

Наблюдавшееся поведение:

- запрос создается сайтом сразу после выбора файла в HTML input;
- формат — `multipart/form-data`;
- синтетическое PNG-изображение без персональных/медицинских данных получило успешный HTTP `200`;
- после ответа карточка документа появилась в composer;
- сообщение в чат автоматически не отправилось.

Названия multipart-полей и структура ответа намеренно не закрепляются в мобильном приложении: ими владеет текущая версия сайта. Нативный мост возвращает WebView только один или несколько локальных `content://` URI через стандартный file chooser callback.

## Проверенный flow запросов

```text
GET /app/chat
  └─ 307 /                         если сессии нет
       ├─ GET /api/auth/get-session
       ├─ GET /api/signup-modal
       ├─ POST /api/auth/email-otp/send-verification-otp
       ├─ POST /api/auth/sign-in/email-otp
       └─ GET /api/auth/get-session
            └─ GET /app/chat
                 └─ выбор файла в <input multiple>
                      └─ POST /api/documents (multipart/form-data)
                           └─ карточка файла в composer
                                └─ ручная отправка пользователем
```

## Внешние запросы

На публичном сайте наблюдались запросы к сервисам Google, Amplitude, Meta и Stripe. Это поведение самого сайта.

Решение для оболочки:

- не добавлять отдельную нативную аналитику;
- не передавать нативной аналитике имена, размеры или содержимое документов;
- по умолчанию не блокировать запросы сайта, чтобы не сломать авторизацию или продуктовый flow;
- внешние main-frame ссылки открывать системным браузером, сохраняя внутренние переходы `app.healz.ai` в WebView.

## Что требует повторной проверки при изменении сайта

- наличие стандартного file input и атрибута `multiple`;
- редирект неавторизованного `/app/chat`;
- появление файла в composer до ручной отправки;
- cookie persistence после обновления WebView/Android;
- выбор кейса и чата через публичную навигацию;
- фактические серверные ограничения по размеру и числу файлов.
